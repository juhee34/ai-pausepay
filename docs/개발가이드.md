# 우니스 개발 가이드 (팀 내부용)

> 원본: claude.ai 문서 '우니스 개발 가이드 (팀 내부용)' (2026-09-29 작성). 기능 범위는 이후 docs/PRD.md 기준으로 바뀌었습니다 — 이 문서와 다르면 PRD가 우선입니다.

비전공자 2인이 **10~11월**에 Claude Code로 우니스 웹앱을 만듭니다. **중간고사 1주 전(10/13)부터 시험이 끝나는 10/26까지는 쉬고**, 10/27부터 5주 동안 집중합니다. 모든 할 일에는 팀원이 직접 할지, 멘토에게 요청할지 표시했습니다. 기능을 8개로 줄인 이유는 검토 · 디벨롭, 가져다 쓸 코드와 다른 팀 사례는 참고 자료 탭에 있습니다.

## 2. 팀원이 할 일 vs 멘토에게 요청할 일

**팀원**: 기획(자료·설문·스케치), 만들기(Claude Code), AI 프롬프트, 폰 확인, 협업(커밋·PR), 운영(참가자·동의서·인터뷰), 분석(사용 기록·발표). **멘토 요청(회당 30분)**: 10/12 배포·키 보관 확인 · 10/28 AI 호출 서버 코드 점검 · 11/11 Supabase 표·접근 규칙 · 11/25 발표 전 보안·비용 점검 · 그 외엔 오래 막혔을 때만.

## 3. 웹을 만드는 순서

**앱 전체는 이 순서로 쌓습니다.**

| 순서 | 무엇을                              | 언제          |
|------|-------------------------------------|---------------|
| 1    | 빈 앱 만들고 인터넷 주소에 올리기   | 10/1 ~ 10/12  |
| 2    | 하단 탭바, 카드·버튼 같은 공통 부품 | 10/1 ~ 10/12  |
| 3    | 기능을 하나씩 (아래 7단계 반복)     | 10/27 ~ 11/23 |
| 4    | 폰 안 저장 → 서버 저장(Supabase)    | 11/10 ~ 11/16 |
| 5    | 사용 기록 남기기                    | 11/10 ~ 11/16 |
| 6    | 디자인 통일, 오류 수정              | 11/24 ~ 11/28 |

**기능 하나는 항상 이 7단계로 만듭니다.**

1.  자료 준비
2.  종이에 그리기
3.  계획 받기 (Claude Code 계획 모드)
4.  화면 만들기 (AI 없이, 가짜 데이터)
5.  AI 연결
6.  **폰에서 확인**
7.  저장·공유 (커밋 → PR → 배포)

- **3단계가 핵심**입니다. 바로 만들어 달라고 하지 말고, 무엇을 어떻게 만들지 계획부터 받아 읽어 봅니다.

- **4단계는 AI 없이** 화면만 먼저 만듭니다. 가짜 데이터를 넣어 모양을 확인한 뒤 5단계에서 AI를 붙이면 문제가 어디서 생겼는지 찾기 쉽습니다.

- **6단계를 넘기면 끝이 아닙니다.** PC에서만 보고 넘어가면 폰에서 글자가 잘리거나 버튼이 안 눌리는 일이 많습니다.

### 도구와 폴더 구조

| 역할      | 도구                               | 한 줄 설명                                                |
|-----------|------------------------------------|-----------------------------------------------------------|
| 웹앱 뼈대 | Next.js                            | 화면과 서버 코드를 한 곳에. AI 열쇠를 서버에 숨길 수 있음 |
| 디자인    | Tailwind CSS + shadcn/ui           | 모던한 카드·버튼 부품을 가져다 씀. 폰 화면 먼저           |
| AI        | Claude API (+ 웹 검색 도구)        | PDF 읽기, 날짜 뽑기, 요약·퀴즈·메일, 출처 달린 리서치     |
| 저장      | 브라우저 저장소 → 4회차에 Supabase | 개인 데이터는 폰에만, 익명 사용 기록만 서버로             |
| 배포      | Vercel                             | push하면 자동으로 주소에 반영                             |
| 협업      | GitHub                             | 코드 합치기와 기록                                        |

**설치**: Git · Node.js(LTS) · VS Code · GitHub CLI · Claude Code (유료 요금제 또는 API 크레딧 필요)

    unis/
    ├─ app/
    │  ├─ page.tsx       ← 홈 = 오늘의 브리핑
    │  ├─ focus/         ← 집중 모드
    │  ├─ calendar/      ← 강의계획서 → 캘린더
    │  ├─ mail/          ← 교수님 메일
    │  ├─ exam/          ← 시험 대비 팩 (요약 + 퀴즈)
    │  ├─ research/      ← 리서치 (+ 발표 목차)
    │  ├─ career/        ← 스펙 영수증
    │  ├─ graduation/    ← 졸업요건 라이트
    │  └─ api/           ← AI 호출 (열쇠는 여기서만)
    ├─ components/       ← 공통 부품
    ├─ CLAUDE.md         ← Claude Code용 설명서
    └─ .env.local        ← API 열쇠 (절대 커밋 금지)

**API 열쇠는** **`.env.local`에만.** 깃허브에 올라가면 누구나 우리 돈으로 AI를 씁니다. 배포할 때는 Vercel 설정에 따로 넣고, 콘솔에서 월 사용 한도도 걸어 둡니다.

## 5. Claude Code 사용법

Claude Code는 말로 설명하면 파일을 읽고, 코드를 쓰고, 명령을 실행하는 AI 팀원입니다. 우리 일은 **무엇을 만들지 정하고, 결과를 폰에서 확인하는 것**입니다. 아래 내용은 [Claude Code 공식 모범 사례](https://code.claude.com/docs/ko/best-practices)와 [빠른 시작](https://code.claude.com/docs/en/quickstart)를 기준으로 정리했습니다.

### 5-1. 설치하고 처음 켜기

1.  **설치**: 터미널에 아래 한 줄을 붙여 넣습니다. 터미널이 낯설면 Claude 데스크톱 앱에서도 Claude Code를 쓸 수 있습니다.

        # 맥
        curl -fsSL https://claude.ai/install.sh | bash
        # 윈도우 (PowerShell)
        irm https://claude.ai/install.ps1 | iex
        # 설치 확인: 버전 번호가 나오면 성공
        claude --version

2.  **로그인**: 레포 폴더로 이동해 `claude`를 입력하면 브라우저 로그인이 뜹니다. Claude Pro 이상 구독 또는 Console 크레딧이 필요합니다.

3.  **첫 질문**: 이 프로젝트가 무엇인지, 폴더 구조를 설명해 달라고 물어봅니다.

4.  **설명서 만들기**: `/init`을 입력하면 CLAUDE.md 초안이 생깁니다. 아래 우리 규칙을 덧붙이고 깃허브에 올려 두 사람이 같이 씁니다.

    # 우니스 (광운대생을 위한 AI 비서 웹앱)

    ## 팀 상황
    - 2인 팀, 둘 다 코딩 초보. 설명은 한국어로 쉽게.
    - 바꾸기 전에 무엇을 어떻게 바꿀지 먼저 설명할 것.

    ## 기술
    - Next.js(App Router) + Tailwind CSS + shadcn/ui, 배포는 Vercel
    - AI는 Claude API. API 키는 app/api 안의 서버 코드에서만 사용
    - 개인 데이터는 localStorage, 익명 사용 기록만 Supabase

    ## 디자인
    - 폰 화면(폭 375px) 먼저, 포인트 색 1개, 둥근 카드, 넓은 여백

    ## 규칙
    - 기능별 폴더: focus, calendar, mail, exam, research, career, graduation
    - .env.local은 절대 커밋하지 않는다
    - main 브랜치에 직접 커밋하지 않는다
    - 다른 레포를 참고하면 출처를 주석으로 남긴다

### 5-2. 한 번의 작업은 항상 4단계

| 단계         | 어떻게                                                                                                  | 이렇게 말합니다                                                   |
|--------------|---------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------|
| 1\. 살펴보기 | `Shift+Tab`을 눌러 화면 아래가 계획 모드(plan mode)가 되게 합니다. 이 모드에서는 파일을 고치지 않습니다 | calendar 폴더를 읽고 지금 어떻게 돼 있는지 설명해 줘              |
| 2\. 계획     | 바꿀 파일과 순서를 계획으로 받고, 읽어 보고 고칩니다                                                    | 날짜 확인 화면을 추가하려면 어떤 파일을 바꿔야 해? 계획을 세워 줘 |
| 3\. 만들기   | 계획 모드를 나와서 진행시킵니다. 확인 방법까지 같이 말합니다                                            | 계획대로 만들고, npm run dev로 화면이 뜨는지 확인해 줘            |
| 4\. 저장     | 폰에서 확인한 뒤 커밋과 PR까지                                                                          | 바뀐 내용을 커밋하고 내 브랜치에 push한 뒤 PR을 만들어 줘         |

오타 수정처럼 한 문장으로 설명되는 일은 계획 없이 바로 시켜도 됩니다.

### 5-3. 꼭 알아야 할 키와 명령

| 키 · 명령                   | 하는 일                                   | 이럴 때                                            |
|-----------------------------|-------------------------------------------|----------------------------------------------------|
| `Shift+Tab`                 | 모드 바꾸기 (계획 모드 등)                | 큰 작업을 시작하기 전                              |
| `Esc`                       | 진행 중인 작업 멈추기                     | 엉뚱한 방향으로 갈 때                              |
| `Esc` 두 번 또는 `/rewind`  | 이전 대화·코드 상태로 되돌리기            | 방금 바꾼 게 맘에 안 들 때                         |
| `/clear`                    | 대화를 새로 시작                          | 다른 기능으로 넘어갈 때, 두 번 고쳤는데도 안 될 때 |
| `/compact`                  | 긴 대화를 요약해서 공간 확보              | 한 기능을 오래 작업할 때                           |
| `@파일이름`                 | 파일을 직접 지정                          | "@app/mail/page.tsx 에서..."                       |
| 이미지 붙여넣기·끌어놓기    | 화면 캡처를 보여 주기                     | 스케치나 깨진 화면을 보여줄 때                     |
| `claude -c` / `claude -r`   | 마지막 대화 이어서 / 목록에서 골라 이어서 | 어제 하던 작업을 이어갈 때                         |
| `/btw`                      | 대화에 남지 않는 짧은 질문                | 용어 뜻만 잠깐 물을 때                             |
| `/help`                     | 명령 목록 보기                            | 기억이 안 날 때                                    |
| `/exit` 또는 `Ctrl+D` 두 번 | 종료                                      | 작업을 마칠 때                                     |

### 5-4. 좋은 요청 공식

**어디에** + **무엇을** + **어떻게 보이게** + **확인 방법** + 먼저 계획만 보여 줘

| 이렇게 말고          | 이렇게                                                                                                                                                                |
|----------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 메일 기능 만들어 줘  | mail 폴더에 교수님 메일 작성기를 만들어 줘. 상황 5개 중 하나를 고르고 과목명·학번·하고 싶은 말을 넣으면 초안이 나오는 화면이야. 폰 폭에 맞춰 줘. 먼저 계획만 보여 줘. |
| 안 돼                | (오류 메시지를 그대로 붙여 넣고) 이 오류가 떠. 원인을 쉬게 설명하고 고친 뒤, 화면이 뜨는지 확인해 줘.                                                                 |
| 예쁘게 해 줘         | (스케치 사진을 붙여 넣고) 이 그림처럼 만들어 줘. 버튼은 아래에 꽉 차게, 카드는 둥글게. 다 만들면 다른 점을 나열해 줘.                                                 |
| 기능 세 개를 한 번에 | 한 번에 하나씩. 끝나면 확인 → 커밋 → `/clear` → 다음                                                                                                                  |

### 5-5. 기능을 시작하기 전: Claude가 우리를 인터뷰하게 하기

무엇을 물어봐야 할지도 모를 때 쓰는 방법입니다. 인터뷰가 끝나면 `/clear`로 새 대화를 열고 SPEC.md를 보며 만들게 합니다.

    우니스에 [교수님 메일 작성기]를 만들고 싶어.
    코딩 초보인 우리에게 화면, 입력칸, 예외 상황, 어려운 점을 하나씩 질문해서 인터뷰해 줘.
    다 물어본 뒤 SPEC.md에 만들 내용, 안 만들 내용, 확인 방법을 정리해 줘.

### 5-7. 오류가 났을 때

1.  오류 메시지 **전체를 복사**해서 그대로 붙여 넣고, 원인을 쉬게 설명한 뒤 고쳐 달라고 합니다.

2.  화면이 이상하면 **캡처를 붙여 넣고** 무엇이 기대와 다른지 말합니다.

3.  같은 문제를 두 번 고쳤는데도 안 되면 `/clear` 후, 배운 점을 넣은 더 자세한 요청으로 다시 시작합니다.

4.  방금 바꾼 게 더 나빠졌다면 `Esc` 두 번(또는 `/rewind`)으로 되돌립니다.

5.  그래도 안 되면 멘토에게 질문합니다.

### 5-8. 안전 규칙

- 모르는 명령을 승인하기 전에 이 명령이 무엇을 하는지 먼저 물어봅니다.

- 잘 되면 바로 커밋합니다. 되돌아갈 자리가 생깁니다. (되돌리기 기능은 깃을 대신하지 않습니다.)

- 이해 안 되는 코드는 초보가 알아듣게 설명해 달라고 합니다. 발표 예상 질문 5번에 대비하는 일입니다.

- API 키는 채팅에 붙여 넣지 않고 `.env.local`에만 직접 넣습니다.

## 6. 깃허브 협업 가이드

핵심은 하나입니다. **main에는 직접 올리지 않고, 내 브랜치에서 작업한 뒤 PR로 합칩니다.** 이 약속만 지키면 서로의 코드를 덮어쓰는 사고가 거의 생기지 않습니다.

### 용어 먼저

| 용어             | 비유                   | 하는 일                                          |
|------------------|------------------------|--------------------------------------------------|
| 레포지토리(repo) | 공유 폴더              | 우니스 코드가 모두 들어 있는 곳                  |
| clone            | 폴더 내려받기          | 깃허브의 레포를 내 컴퓨터로 처음 복사 (최초 1번) |
| commit           | 저장 버튼 + 메모       | 지금까지 고친 내용을 한 덩어리로 기록            |
| push             | 올리기                 | 내 commit을 깃허브로 보냄                        |
| pull             | 내려받기               | 팀원이 올린 변경을 내 컴퓨터로 가져옴            |
| branch           | 내 작업 공간           | main을 건드리지 않고 따로 작업하는 갈래          |
| PR(Pull Request) | "이거 합쳐도 돼?" 요청 | 내 브랜치를 main에 합치기 전에 팀원이 확인       |
| merge            | 합치기                 | PR을 main에 합침                                 |

### 처음 한 번만 하는 설정

1.  초대받은 팀원은 이메일이나 깃허브 알림에서 초대 수락(Accept) 버튼을 눌러야 합니다. 안 누르면 push가 거부됩니다.

2.  터미널(맥: 터미널, 윈도우: Git Bash)을 열고 내 이름과 깃허브 이메일을 등록합니다.

    git config --global user.name "홍길동"
    git config --global user.email "깃허브에_가입한_이메일"

3.  깃허브 로그인은 GitHub CLI로 하는 게 가장 쉽습니다. 설치 후 아래를 입력하고 브라우저로 로그인합니다.

    gh auth login

4.  작업할 폴더로 가서 레포를 내려받습니다. 주소는 레포 페이지의 초록색 **Code** 버튼에서 복사합니다.

    cd ~/Documents
    git clone https://github.com/계정이름/레포이름.git
    cd 레포이름

### 매일 작업 순서 (이것만 외우면 됩니다)

1.  **최신 받기** — 작업 전에 항상 main을 최신으로 맞춥니다.

        git switch main
        git pull

2.  **내 브랜치 만들기** — 기능 하나에 브랜치 하나.

        git switch -c feature/mail

3.  **작업하기** — Claude Code와 함께 코드를 고치고, 화면이 잘 나오는지 확인합니다 (`npm run dev` 후 브라우저에서 `localhost:3000`).

4.  **저장하기(commit)** — 의미 있는 단위마다 자주 합니다.

        git status                 # 무엇이 바뀌었는지 확인
        git add .                  # 바뀐 파일 모두 담기
        git commit -m "feat: 메일 작성기 체크리스트 추가"

5.  **올리기(push)** — 첫 push만 `-u origin 브랜치이름`을 붙이고, 그다음부터는 `git push`만.

        git push -u origin feature/mail

6.  **PR 만들기** — 깃허브 레포 페이지에 뜨는 **Compare & pull request**를 누르고, 무엇을 했는지 두세 줄 적습니다.

7.  **확인 후 합치기** — 팀원이 PR을 열어 보고 **Merge pull request**를 누릅니다. 합쳐지면 Vercel이 자동으로 새 버전을 배포합니다.

8.  **다시 1번으로** — 다음 기능은 다시 `git switch main` → `git pull`에서 시작합니다.

### 우리 팀 약속

| 항목        | 규칙                                     | 예시                                                                                        |
|-------------|------------------------------------------|---------------------------------------------------------------------------------------------|
| 브랜치 이름 | `feature/기능이름`, 고칠 때는 `fix/내용` | `feature/calendar`, `fix/timer-reset`                                                       |
| 커밋 메시지 | `종류: 한 일` (한글 OK)                  | `feat: 퀴즈 채점 추가`, `fix: 타이머 멈춤 해결`, `style: 버튼 색 변경`, `docs: README 수정` |
| PR 확인     | 내 PR은 팀원이 merge. 하루 안에 확인하기 | 카톡에 PR 링크 공유                                                                         |
| 담당 파일   | 상대 담당 폴더는 미리 말하고 고치기      | 공통 부품(`components/`)은 특히 조심                                                        |

### 절대 하지 말 것

- `.env.local`(API 열쇠) 커밋하기 — `.gitignore`에 들어 있는지 확인합니다.

- `git push --force` — 팀원의 작업을 지울 수 있습니다.

- main에서 바로 작업하고 push하기.

### 충돌(conflict)이 났을 때

두 사람이 같은 줄을 고치면 깃이 어느 쪽을 남길지 묻습니다. 당황하지 말고:

1.  VS Code에서 충돌된 파일을 열면 **Accept Current / Accept Incoming / Accept Both** 버튼이 보입니다. 남길 쪽을 고릅니다.

2.  헷갈리면 Claude Code에게 "충돌이 났어. 양쪽이 뭘 바꿨는지 설명하고, 둘 다 살리는 방향으로 해결해 줘"라고 부탁합니다.

3.  저장한 뒤 `git add .` → `git commit` → `git push`.

### 자주 만나는 오류

| 오류 메시지에 이런 말이 있으면            | 뜻                             | 해결                                      |
|-------------------------------------------|--------------------------------|-------------------------------------------|
| `rejected` / `fetch first`                | 깃허브에 내가 없는 변경이 있음 | `git pull` 후 다시 `git push`             |
| `Permission denied` / `403`               | 권한 없음                      | 초대 수락 여부, `gh auth login` 다시 하기 |
| `not a git repository`                    | 레포 폴더 밖에 있음            | `cd 레포이름`으로 이동                    |
| `Your local changes would be overwritten` | 저장 안 한 변경이 있음         | 먼저 commit하고 pull                      |

## 7. 매 회차 체크리스트

회차를 시작할 때와 끝낼 때, 두 사람이 10분씩 같이 확인합니다.

**시작할 때**

- [ ] 이번 회차에 누가 어떤 기능을 맡는지 다시 확인
- [ ] 두 사람 다 `git switch main` → `git pull`로 최신 상태에서 출발
- [ ] 각자 기능 브랜치 만들기

**끝낼 때**

- [ ] 열려 있는 PR을 모두 merge했다
- [ ] Vercel 주소를 **휴대폰으로** 열어서 이번 기능이 동작한다

- [ ] 회차별 계획의 **끝났다는 기준**을 만족한다
- [ ] 못 끝낸 일은 다음 회차로 넘기거나 빼기로 정했다
- [ ] 발표용 화면 캡처를 한 장씩 남겼다

## 기술 검수 — 실제로 만들 때 막히는 지점

가장 큰 위험은 기능이 아니라 **로그인 없이 브라우저에 저장하는 구조**입니다. 아이폰 사파리는 7일 동안 열지 않은 사이트의 저장 데이터를 지우는데, 이 한 가지가 기록 보존·재방문률·알림 세 곳에 영향을 줍니다. 아래 대응은 개발 가이드의 주차별 할 일 표에 넣었습니다 (10/4 추가).
